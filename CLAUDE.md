# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Translator: настольное приложение на Tauri 2 (Rust) и Svelte 5 для перевода игр на Ren'Py на русский, с графом сцен, глоссарием и LLM: локальными (LM Studio, Ollama) и внешними (ChatGPT, Claude, Gemini). Парсер спрятан за трейтом `GameParser`, но реализован только Ren'Py.

## Команды

Из корня проекта:

```bash
npm install
npm run tauri dev
npm run tauri build
npm run check
node --test tests/*.test.mjs
node --test --test-name-pattern="focused mode" tests/scene-graph.test.mjs
```

Скрипта `npm test` нет. Тесты импортируют `.ts` напрямую, поэтому нужен Node с нативной загрузкой TypeScript.

Из `src-tauri`:

```bash
cargo test --lib
cargo test --lib test_saved_edits_survive_line_shifts
cargo test --lib -- --ignored
cargo clippy
```

Тесты с `#[ignore]` работают на реальных играх и берут пути из переменных окружения: `TRANSLATOR_TEST_TRANSLATED_GAME`, `TRANSLATOR_TEST_RPA_GAME`, `TRANSLATOR_TEST_CHARACTERS_GAME`, `TRANSLATOR_TEST_RPA2_ARCHIVE`, `TRANSLATOR_TEST_FRAMED_ARCHIVE`, `TRANSLATOR_TEST_TL_DIR`, `TRANSLATOR_TEST_PACKED_TL_GAME`. Без переменной такой тест ничего не проверяет и проходит. `TRANSLATOR_RPYC_PROBE_DIR` включает запись архивов для проверки скомпилированных скриптов настоящим движком.

## Архитектура

Интерфейс почти целиком находится в `src/routes/+page.svelte`. Это SPA без SSR. Команды Tauri объявлены в `src-tauri/src/lib.rs` и регистрируются в `generate_handler!`. Вызовы JS API Tauri, кроме собственных команд, требуют разрешений в `src-tauri/capabilities/default.json`: `core:default` и `opener:default` покрывают не всё.

### Главные инварианты

- **Чтение игры и явная установка.** Правки, кэш и экспорт пишутся в `%LOCALAPPDATA%\TranslatorApp\projects_cache\<имя>_<хэш пути>`: `scripts/` (скрипты из RPA), `translations/*.json` (правки), `glossary.json`, `scene_notes.json` (заметки модели по частям сцен), `exports/`, `unpacked/`. Произвольный вывод в игру запрещает `ensure_output_outside_game`. Явные команды `install_mod` и `remove_mod` устанавливают/удаляют только `game/ru_lang.rpa`; установка атомарно заменяет архив, не трогая `tl/russian` и оригиналы.
- **Панику в Rust нельзя допускать на данных игры.** В релизе `panic = "abort"`, поэтому паника закрывает приложение. Файлы игр считаются недоверенными: разбор возвращает `Err`, а архивы проверяются на выход за пределы папки (`safe_output_path`).
- **Путь оценивается относительно корня игры.** Папка `tl` может встретиться и выше игры, поэтому файл перевода определяют `is_translation_path` и `tl_relative_name`, а не подстрока пути.
- **CSP действует только в сборке.** В `tauri dev` страница грузится с dev-сервера напрямую, поэтому правила из `tauri.conf.json` проверяются на `tauri build`. Интерфейс не обращается к сети сам: запросы к нейросети идут из Rust.
- **Запуски модели идут по одному.** Остановка общая на все запросы. Новое действие через модель начинается с `beginLlmRun` (`llm-run.svelte.ts`), его кнопки и настройки отключаются по `llmRun.active`, а команда в Rust получает флаг остановки только из `LlmRun::begin`, который откажет второму запуску. Запуск идёт и при закрытом глоссарии, а открытие перечитывает его с диска, поэтому итог записывается в запись, найденную по коду после ответа модели, а не в объект, взятый до запроса.
- **Язык задан константой.** `TL_LANG` в `lib.rs` равен `russian`, то же значение записано в `SourceViewerModal.svelte`.

### Поток данных

1. **Скан** (`scan_game_project`): `refresh_script_cache` складывает в `scripts/` то, что нельзя прочитать прямо из папки игры: содержимое `.rpa` и `.rpyc` без `.rpy` рядом, декомпилированные в `.rpy`. Как и в движке, скрипт на диске важнее архива, поэтому его копии в кэше нет. Если кэшировать нечего, папка удаляется. Затем собираются персонажи и список файлов: перевод `tl/russian` с диска и из кэша, а если его нет, скрипты из кэша и из папки игры. Прогресс файла с сохранёнными правками считается с их учётом. Папка `_mods` и свой архив `ru_lang.rpa` при этом пропускаются.
2. **Разбор** (`parse_project_file`): `RenpyParser` строит `ScenarioGraph` из файла перевода или оригинала, а структура сцен и переходов берётся из оригинала (`resolve_original_script`, в том числе из кэша). Кнопки экранов дают переходы от сцен, показавших экран, через весь проект (`screen_targets`, `screen_edges`). Результат кэшируется по времени изменения файлов. Текст для нейросети и сцены персонажа в глоссарии (`scenes.rs`) собираются этим же разбором из оригиналов на диске и в кэше (`original_scripts`). Удалённые персонажи с кодом запоминаются в глоссарии (`removed_characters`), иначе скан вернул бы их. У одного героя может быть несколько кодов: `merged` в записи глоссария объединяет их реплики и сцены, а скан не возвращает такие коды отдельными записями. Запись без кода в `merged` не попадает: при объединении она становится формой (`cleanCharacterForms`). В реплики для модели подставляются значения строковых переменных из скриптов, а значение токена из глоссария заменяет токен целиком, как в игре, или описание в скобках, если значения нет (`tokens`): имя токена модель не видит, иначе верит ему больше, чем пояснению. Переводы упомянутых имён с полом и заполненные термины передаются отдельными строками (`names`, `terms`) и не входят в ключ заметки. Запросы ограничены по объёму текста, чтобы уместиться в окно контекста. Термины находятся без модели по всем репликам (`terms.rs`) и считаются один раз на скан (`term_candidates`). Отдельного состояния у них нет: раздел «Новые» в списке терминов показывает все найденные названия, которых нет в глоссарии, поэтому взятая запись уходит из него сама, а удалённая возвращается. Что взять, решает пользователь, а перевод даёт обычный запуск по терминам. Мусорные названия уходят в корзину (`discarded_terms` в глоссарии), откуда их можно вернуть в новые. У термина и персонажа есть другие формы (`forms`): сокращение или обращение со своим переводом. Они входят в поиск сцен, поиск записей, подсказки связи и подсказки модели. У персонажа есть имя и фамилия с переводами (`first_name`, `last_name`, `translated_first_name`, `translated_last_name`) и другие формы (`forms`), других имён у записи нет. Имя подставляет скан, фамилию вносит пользователь. Из них складывается подпись карточки (`characterTitle`) и подпись говорящего в тексте для модели (`full_name`), поэтому смена имени или фамилии меняет ключи заметок. Реплики персонажа находятся по коду (`aliases`), а упоминания по имени, фамилии и формам (`names`). Старые поля `card_name`, `original_name` и `translated_name` читаются только для переноса при загрузке (`adopt_card_name`, `adopt_name_from_game`): имя из игры, не совпавшее с именем и фамилией, становится формой. Одна форма может быть у нескольких записей, например фамилия: тогда в подсказках модели остаётся её перевод без пола, а если переводы расходятся, подсказки нет (`knownNames`). Термин или название, переданное персонажу, уходит в корзину, а у персонажа появляется форма: связи между ними нет, поэтому у формы персонажа нет кнопки «В термин». Из корзины название можно передать ещё одному персонажу, поэтому общую фамилию получают все. Формы чистятся при загрузке глоссария, объединении, передаче и выходе из полей имени и фамилии (`uniqueForms`): уходят пустые строки и копии других форм, имени из игры, имени, фамилии и полного имени, иначе одно написание получит два перевода и `knownNames` уберёт подсказку. Перевод лишней формы переходит в пустое поле. Формы предлагает `name-forms.ts`, а связывает записи только пользователь: совпадение букв и слов ещё не значит одну и ту же запись. Запись связывается поиском в `OwnerSelect`, а новым персонажем становится отдельной кнопкой, после которой открывается его запись: только у персонажа есть род, написание имени всей группой и сцены с упоминаниями. Кода в скриптах у него нет, поэтому `alias` такой записи это внутренний номер с `~`, который не показывается (`hasScriptCode`). Имена можно обновить всей группой (`translate_names`): модель видит весь состав игры и определяет происхождение каждого имени. Запуск идёт в два шага: сначала имена и фамилии, а у кого их нет, имя из игры (`baseNames`), затем остальные формы от готового написания (`formNames`), причём заполненное поле важнее ответа первого шага. Фамилия идёт с полом, потому что её перевод может от него зависеть, поэтому у семьи она может различаться. Запросы и ответы связаны по `id`, а повторы объединяет интерфейс. Замены отбирает пользователь: запрос заново пишет и заполненные имена, поэтому такие строки по умолчанию не отмечены. Пояснения токенов предлагает модель (`suggest_tokens`): она читает реплики с `[___]` вместо токена, а в глоссарий их отбирает пользователь. Имена и термины можно перевести и без API: кнопка копирует в буфер те же правила и данные в JSON одним текстом (`names_chat_request`, `terms_chat_request`), а вставленный ответ проходит те же проверки и попадает в тот же отбор (`read_names_chat_answer`, `read_terms_chat_answer`). Для имён оба шага идут одним запросом (`chatNames`): формы ссылаются на оригинал, а чат-бот пишет его в этом же ответе. Модель при этом не запускается, поэтому `LlmRun` не нужен. Запуски находятся в панели под вкладками глоссария (`GlossaryAiPanel`). Подключения и их модели по умолчанию задаются в настройках LLM (`llm-settings.ts`), действие может выбрать своё подключение и модель в `LlmChoice` (раздел панели, а для описаний и карточка персонажа, выбор один и тот же), а в команды они приходят как `ChatTarget`. Этот выбор разовый: он не сохраняется и сбрасывается при открытии глоссария, чтобы запрос не ушёл случайно на сервер, выбранный раньше. Его `provider` определяет вид запроса (`call_chat_completion`): Claude вызывается напрямую через Messages API, ChatGPT получает `max_completion_tokens` без `temperature`, а Gemini идёт через OpenAI-совместимый адрес. Итог каждого пакета приходит в окно через `Channel` и может отстать от итога команды, а `cancel_llm_run` останавливает обработку между пакетами. Сцены персонажа читаются частями из целых сцен: часть дополняется подходящими ближайшими сценами (`pack_scenes`). Описание персонажа по заметкам собирается и после остановки чтения. Части видны в окне персонажа до запуска, вместе со сценами и тем, что получит модель. Группа персонажей обновляется на вкладке «Персонажи» тем же путём, по очереди: параметры задают минимум и максимум частей и желаемый процент для каждой записи (`ReadingDepthSettings`, `partsForDepth`). Процент от общего числа частей округляется вверх и ограничивается минимумом и максимумом; у кого частей меньше минимума, тот читается целиком. Готовые части сохраняются даже сверх максимума. Для одиночного запуска в карточке остаётся один слайдер числа частей; минимум, максимум и процент применяются только к массовому обновлению (по умолчанию 5, 50 и 30%). Заполненная запись, которой параметры не добавляют новых частей, в запуск не входит, а собрать её заново можно в карточке. Заметки можно сбросить (`reset_character_notes`) или исключить из описания (`excluded_notes`). Термины обновляются тем же путём (`summarize_term`): сцены дают реплики с термином и его формами, заметки лежат в том же файле под хозяином `term:<id>`, а итог записывается в его описание. На вкладке терминов панель и карточка используют те же разделы, что у персонажей. Описания сцен лежат в глоссарии под меткой сцены (`scenes`), поэтому не зависят от файла и номера строки. Список сцен с числом реплик собирается по `game_lines` (`game_scenes`), реплики вне меток сценой не считаются, а описание пропавшей сцены остаётся. Обновляются они тем же путём, что персонажи и термины (`summarize_scene`): части это реплики самой сцены, заметки лежат под хозяином `scene:<метка>`, а заметка единственной части сразу становится описанием, поэтому сборка ей не нужна. Название сцены (`title`) пишется по готовому описанию отдельным запросом и только в пустое поле: заполненное мог задать пользователь, а сбой этого запроса не отнимает описание. Оно называет роль сцены в сюжете, а не её самый заметный поступок, поэтому первой сцене игры запрос сообщает, что она первая (`OPENING_SCENE_NOTE`). Запись держится, пока заполнено хотя бы одно из полей. В интерфейсе название показывается везде вместе с меткой (`sceneLabel`, `SceneName`), а поиск сцен находит и по нему. Метку модель не видит (`SCENE_NAME`), а говорящих подписывают имена из сохранённого глоссария (`scene_parts_of`). Запись есть только у описанной сцены, поэтому в общем пути сцену представляет `SceneTarget`, а исключать части и заметки у неё нельзя. В группе сцен по умолчанию ничего не выбрано: их тысячи, и незаполненной оказалась бы почти вся игра.
3. **Правки** (`translation.rs`): игровые файлы не меняются, правки лежат в JSON по ключу `LineKey`. Он не зависит от номера строки: `Block` для блоков `translate`, `Strings` для `old`, `Script` для оригинальных скриптов. Старые ключи-массивы переносятся при загрузке.
   Перевод реплик (`translate_file_lines`, `translate_scenes`) запускается над таблицей для открытой сцены или файла и заполняет только пустые строки. Запуск по всему проекту вызывает ту же команду для каждого файла с пустыми строками по очереди (`translateProjectLines`), сохраняя глоссарий между файлами. Сброс перевода сцены или файла записывает пустые правки, как ручная очистка строки, после чего запуск переведёт их заново. Сброс всего проекта (`resetProjectTranslation`) делает то же для каждого файла с переводом и сразу сохраняет правки на диск. Модель получает сохранённое на диске, поэтому перед запуском сохраняются правки и глоссарий. Запрос идёт по одной сцене (`line_batches`, готовые реплики остаются в пакете как контекст, а реплики перед пакетом идут отдельным блоком `Earlier lines`: в общем списке слабая модель переводила их заново под выдуманными номерами) с подписями говорящих, описанием сцены и подсказками глоссария. Токен со значением из глоссария заменяется им до запроса (`fill_token_values`) и переводится как обычный текст. Остальные токены остаются в тексте, модель видит их пояснение (`note`): перевод без всех оставшихся токенов и тегов оригинала отбрасывается (`usable_translation`), и строка остаётся пустой для следующего запуска. Пакет, где после ответа остались пустые реплики, или запрос, который не удался, спрашивается ещё раз (`LINE_ATTEMPTS`). Повтор спрашивает каждую группу пустых реплик подряд отдельным запросом (`blank_runs`): слабые модели бросают конец пакета и пропускают реплики рассказчика, а готовые реплики внутри списка переводили заново вместо пустых. Длинный перевод, совпавший с переводом другой реплики с другим оригиналом, отбрасывается вместе с ней (`accepted_lines`, `MIN_SHIFT_LETTERS`): модель пропускала реплику и подписывала её номером перевод соседней. Сломанный JSON ответа (комментарии, пояснения вне строк, пропущенные кавычки) читается запасным разбором пар номера и перевода (`line_answer`). Реплика без букв вне токенов и тегов вроде «...» или «[mc]!» модели не отправляется и сразу записывается как есть (`is_wordless`): на такие модель отвечала пустым списком. Токен со значением к этому времени уже заменён словом, поэтому «[roommate]!» переводится. Перевод реплики принимается и из поля `translation`, потому что локальные модели повторяют его за репликами контекста. Каждый пакет сразу пишется в правки с пометкой `drafts` (`save_drafts`), и запись не трогает заполненные строки, потому что пользователь мог заполнить их, пока модель отвечала. В таблице это статус «Модель»: любая правка или подтверждение снимает пометку, а экспорт берёт такие строки как обычные. Сцена без описания сначала читается целиком тем же путём, что в глоссарии (`read_scene`): описание идёт в запросы перевода, а интерфейс вносит его только в пустое поле. Отпечаток текста (`text_hash`) лежит рядом с описанием и показывает, что игра изменила сцену после чтения. Новый термин из ответа попадает в глоссарий как предположение (`guess`), только если он есть в тексте пакета и его нет среди записей, имён и корзины (`new_terms`). В запросы предположение идёт с пометкой `(unconfirmed)`, пока его не подтвердит пользователь. Кнопка в строке таблицы переводит одну строку (`translate_single_line`, `translate_line`) с теми же подсказками и проверками. Сцену без описания она не читает. Готовый перевод, не отмеченный как черновик, она заменяет только после вопроса пользователю (`replace_with_draft`).
   Редактура (`review_file_lines`, `review_single_line`, `review_scenes`, `review_line`) запускается вручную для открытой сцены, файла или строки, у неё своё действие `review` в настройках LLM. Модель вычитывает готовые реплики теми же пакетами и с теми же подсказками, что перевод, но реплики пакета идут с полем `draft`, а ответ содержит только исправленные. Правка без токенов и тегов оригинала или без изменений не проходит (`review_fixes`). Исправления заменяют строки сразу, включая подтверждённые, и получают пометку `drafts` (`replace_with_drafts`): по статусу «Модель» их видно в таблице. Строку, которую пользователь правит во время запуска, интерфейс не трогает. Лимит ответа у всех подключений включает запас на размышления (`REASONING_TOKENS`): локальная Gemma тратила на них весь лимит и не писала ответ.
4. **Экспорт** (`build_mod_archive`):
   - В мод входит весь перевод игры: файлы `tl/<язык>` с диска и из архивов (`packed_translation_files`) вместе с картинками и шрифтами. Поэтому мод работает и в копии игры без этого перевода.
   - Правки файлов `tl/<язык>` подставляются в копии этих файлов.
   - Остальные правки становятся строковыми переводами в `translator_saved_strings.rpy`, потому что `id` блоков `translate` вычисляет сам Ren'Py.
   - `translator_language.rpy` включает язык, если в игре нет такого пункта.
   - Всё компилируется и упаковывается в `ru_lang.rpa`, потому что из архивов Ren'Py читает только `.rpyc`.
   - Файлы `tl/russian` на диске Ren'Py читает раньше архива. Перекрывать их не нужно: чтобы применить мод, такой перевод удаляют.

### Форматы Ren'Py

- `pickle.rs`: декодер и кодировщик Python pickle для индексов RPA и деревьев скриптов. Значения считаются деревьями без ссылок, поэтому глубина ограничена `MAX_PICKLE_DEPTH`, а копии из memo `MAX_MEMO_NODES`. Рекурсивный обход `.rpyc` идёт на потоке с большим стеком (`statements_of`).
- `rpa.rs`: чтение и запись архивов RPA-2.0 и RPA-3.0.
- `rpyc.rs`: декомпиляция в упрощённый `.rpy` только для разбора, не для повторной компиляции игрой. Отступы сохраняют вложенность `menu` и `if`: по ним `parse_script_structure` строит выборы и условия. От экранов остаются только связи: `action` с `Jump`/`Call`/`Show` и `use`, а также `call screen` и `show screen` в сценах. Файлы перевода восстанавливаются точнее (`decompile_translation`): блоки `translate`, строки `old`/`new` и комментарии с оригиналом, найденным по `id`. В `.rpyc` игры `id` не хранятся, их считает `DialogueIdentifiers` так же, как `Restructurer` в движке, поэтому `say_code` повторяет `Say.get_code`. Оператор, который нельзя восстановить, записывается как `<Класс>`, чтобы правка такого файла остановила сборку. Если вывод декомпилятора меняется, нужно поднять `CACHE_VERSION` в `rpa.rs`, иначе останется старый кэш.
- `rpyc_writer.rs`: компилятор `.rpyc` без запуска игры. Формат определяется по файлам движка (`ScriptFormat::detect`), поддерживаются три раскладки `AstLayout`. Компилируются только строковые переводы, блоки `translate` с репликами (включая аргументы, атрибуты после `@`, `nointeract` и `with`) и `init python`, остальное останавливает сборку.

### Состояние в памяти

Статические кэши в `lib.rs` (`PARSED_FILE_CACHE`, `SCRIPT_STRUCTURE_CACHE`, `PROJECT_CACHE`) сбрасываются при сохранении правок и очистке кэша. Разобранные реплики (`game_lines`) и кандидаты в термины готовятся в фоне после скана, реплики идут в порядке сюжета (`story_order`), и всё это живёт до следующего скана. Параллельные запросы реплик ждут один разбор. `find_game_root` определяет корень игры по открытым проектам (`project_roots`), а для остальных файлов по признакам на диске. От него зависит путь к хранилищу правок. Папка данных проекта привязана к пути игры, поэтому после переезда или в новой версии правки и глоссарий переносятся явно (`transfer_project_data`). Запись одного файла или папки сериализуется через `path_lock`.

## Соглашения

- Комментарии и сообщения для пользователя пишутся на русском.
- Команды Tauri возвращают `Result<_, String>`, а работу с диском выполняют в `spawn_blocking`.
- Сообщения коммитов следуют Conventional Commits на английском.
